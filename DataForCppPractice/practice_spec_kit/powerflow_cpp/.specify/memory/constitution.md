# PowerFlow C++ Constitution

## Core Principles

### I. Modular Architecture

Каждый этап расчета установившегося режима MUST быть реализован как независимый
модуль с четко определенным интерфейсом. Последовательность обработки:
чтение JSON → формирование матрицы проводимостей → решение СЛАУ → расчет
потоков → вывод результатов. Каждый модуль SHOULD быть тестируем изолированно.
Зависимости между модулями MUST быть однонаправленными и следовать порядку
конвейера обработки данных.

**Rationale**: Модульная архитектура позволяет независимо разрабатывать,
тестировать и модифицировать каждый этап вычислительного конвейера, упрощает
отладку и повторное использование компонентов.

### II. Modern C++ Standards

Кодовая база MUST использовать стандарт C++17. Допустимо использование
возможностей C++20 при условии совместимости с целевыми компиляторами.
Обязательные практики:
- Умные указатели (`std::unique_ptr`, `std::shared_ptr`) вместо голых `new`/`delete`.
- Активное использование STL (контейнеры, алгоритмы).
- `constexpr` для функций и констант, где это уместно.
- `auto` для вывода типа, когда тип очевиден из контекста.
- `snake_case` для имен функций, переменных и пространств имен.
- `PascalCase` для имен классов и структур.
- Обработка ошибок через исключения с информативными сообщениями на русском
  языке.

**Rationale**: Единый стандарт кодирования обеспечивает предсказуемость кодовой
базы, облегчает код-ревью и снижает риск ошибок управления памятью.

### III. Correctness & Test-Driven Verification

Модульные тесты MUST покрывать все вычислительные модули. Обязательные
категории тестов:
- Тесты на простых схемах (2 узла, 3 узла) с известным аналитическим решением.
- Проверка баланса мощностей:
  сумма генерации = сумма нагрузки + потери (потери в линиях не учитываются
  в упрощенной модели DC, т.е. сумма генерации = сумма нагрузки).
- Сравнение результатов с ручным расчетом для малых сетей.
- Проверка корректности работы с граничными условиями (вырожденные матрицы,
  несвязные сети).

Точность вычислений MUST быть не хуже 1e-6 в относительных единицах для всех
величин.

**Rationale**: Точность расчетов установившегося режима критически важна для
практического применения. Тестирование на малых схемах с известным результатом
дает уверенность в правильности алгоритма для больших сетей.

### IV. Domain Model Fidelity

Физическая модель MUST точно соответствовать предметной области:
- Расчеты ведутся для сети постоянного тока (DC power flow).
- В линиях учитываются ТОЛЬКО продольные активные сопротивления R (Ом).
- Потери в линиях не учитываются.
- Переток мощности по параллельным линиям распределяется обратно
  пропорционально их сопротивлениям.
- Используются закон Ома и первый закон Кирхгофа для составления системы
  линейных уравнений.
- Типы узлов: балансирующий (U=const), нагрузочный (P нагрузка), генераторный
  (P генерация).

Математическая модель MUST быть документирована в комментариях к коду, включая
вывод формул для матрицы проводимостей и вектора правой части.

**Rationale**: Точное соответствие физической модели предметной области
гарантирует корректные результаты расчета и возможность верификации
инженерами-электриками.

### V. Input/Output Contract & Observability

Входные данные MUST приниматься в формате JSON с фиксированной схемой:
- `nodes`: список узлов с полями `id`, `name` (опционально), `type`
  (slack/load/generator), `power_MW` (МВт, для load/generator),
  `voltage_kV` (кВ, только для slack).
- `branches`: список ветвей с полями `id`, `name` (опционально),
  `from_node_id`, `to_node_id`, `resistance_ohm` (Ом).
- Глобальные параметры: `base_voltage_kV` (кВ), `base_power_MVA` (МВА),
  `tolerance`, `max_iterations`.

Валидация входного JSON MUST выполняться до начала вычислений: проверка
связности в пределах каждого островка, соответствие количества узлов
ограничению (≤20), корректность типов полей, отсутствие дублирующихся
идентификаторов.

Выходные данные MUST включать:
- Напряжения в узлах (о.е. и кВ).
- Потоки активной мощности по ветвям (МВт).
- Баланс мощностей.

Вывод результатов MUST осуществляться в виде ASCII-таблицы в консоль.
Опционально — формирование текстового файла отчета.

Все ключевые этапы вычислений SHOULD сопровождаться структурированным
логированием для отладки.

**Rationale**: Фиксированный контракт ввода/вывода обеспечивает
воспроизводимость результатов и упрощает интеграцию с внешними инструментами.

## Technical Constraints

- **Язык**: C++17 (GCC ≥ 8, Clang ≥ 7, MSVC ≥ 19.14).
- **Система сборки**: CMake ≥ 3.15.
- **Матричная библиотека**: Eigen 3.4+ (плотные матрицы, размерность до 20×20,
  разреженность не критична).
- **JSON-библиотека**: nlohmann/json 3.11+ (header-only, парсинг и валидация).
- **Тестовый фреймворк**: Catch2 или GoogleTest (на выбор реализации, должно
  быть согласовано в плане).
- **Размерность сети**: максимум 20 узлов.
- **Сеть MUST быть связной в пределах каждого островка**: каждый связный
  компонент (островок) сети MUST содержать ровно один балансирующий узел.
  Все узлы островка MUST быть достижимы от его балансирующего узла.
  Валидация выполняется изолированно для каждого островка: островки с
  ошибками пропускаются с предупреждением, остальные рассчитываются.
- **Структура проекта**:
  ```
  src/       — исходный код (.cpp)
  include/   — заголовочные файлы (.hpp)
  tests/     — модульные тесты
  data/      — примеры JSON-файлов с тестовыми схемами
  CMakeLists.txt
  ```

## Development Workflow & Quality Gates

- **Сборка**: Проект MUST собираться без ошибок и предупреждений (флаги
  `-Wall -Wextra -Wpedantic`) на всех поддерживаемых платформах.
- **Тестирование**: Все модульные тесты MUST проходить (зеленый набор)
  перед принятием изменений. Запуск тестов — `cmake --build build && ctest`.
- **Валидация данных**: Примеры JSON-файлов в `data/` MUST быть валидными и
  покрывать все типовые конфигурации сети (минимальная сеть, параллельные
  линии, смешанные типы узлов).
- **Код-ревью**: Изменения, затрагивающие вычислительное ядро (матрица
  проводимостей, решение СЛАУ, расчет потоков), MUST проходить проверку
  вторым разработчиком.
- **Документирование**: Каждый публичный API (функции в заголовочных файлах)
  MUST иметь документирующий комментарий с описанием параметров, возвращаемого
  значения и возможных исключений.

## Governance

Настоящая конституция является высшим нормативным документом проекта. Все
решения по архитектуре, реализации и процессам разработки MUST соответствовать
изложенным принципам.

**Порядок внесения изменений:**
1. Предложение изменения (Pull Request с описанием и обоснованием).
2. Обсуждение и согласование с командой.
3. Обновление конституции с инкрементом версии (семантическое версионирование).
4. Актуализация связанных артефактов (plan-template, spec-template,
   tasks-template) при необходимости.

**Версионирование конституции:**
- MAJOR: удаление или переопределение принципов (обратно несовместимые
  изменения в управлении проектом).
- MINOR: добавление нового принципа или существенное расширение существующего.
- PATCH: уточнения формулировок, исправления опечаток, не затрагивающие смысл.

**Проверка соответствия**: Каждый план реализации (plan.md) MUST содержать
секцию «Constitution Check», подтверждающую соответствие предлагаемого
технического решения принципам конституции.
