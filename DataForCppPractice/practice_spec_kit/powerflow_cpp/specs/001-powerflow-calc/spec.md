# Feature Specification: Расчет установившегося режима электрической сети постоянного тока

**Feature Branch**: `001-powerflow-calc`

**Created**: 2026-07-01

**Status**: Draft

**Input**: User description: "Разработай спецификацию для программы расчета установившегося режима (УР) электрической сети постоянного тока. Название проекта: PowerFlowCalc..."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Расчет УР по файлу конфигурации сети (Priority: P1)

Инженер-электрик подготавливает JSON-файл с описанием своей электрической сети
(узлы, ветви, базисные величины), запускает программу из командной строки,
передавая путь к файлу, и получает в консоли полный отчет о распределении
активной мощности: напряжения в узлах, потоки по ветвям, сводку баланса.
Опционально формируется текстовый файл отчета для документирования.

**Why this priority**: Это основной пользовательский сценарий — без него
программа не имеет ценности. Все остальные сценарии являются вспомогательными.

**Independent Test**: Подготовить JSON-файл с простейшей сетью (2 узла: slack +
нагрузка, одна ветвь), запустить расчет, проверить корректность напряжений и
потоков, сравнить с ручным расчетом. Результат должен полностью
воспроизводиться.

**Acceptance Scenarios**:

1. **Given** валидный JSON-файл с сетью из 4 узлов (slack, нагрузка, генератор,
   транзитный), **When** инженер запускает программу с путём к файлу, **Then**
   в консоль выводятся три таблицы: напряжения в узлах (о.е. и кВ), потоки
   мощности по ветвям (МВт, направление), сводка баланса (генерация, нагрузка,
   невязка, статус сходимости, число итераций).

2. **Given** валидный JSON-файл и отсутствие аргумента командной строки,
   **When** инженер запускает программу без аргументов, **Then** программа
   использует файл по умолчанию (`data/input.json`) и выполняет расчет.

3. **Given** валидный JSON-файл с параллельными линиями между узлами, **When**
   инженер запускает расчет, **Then** поток мощности по каждой параллельной
   линии распределяется обратно пропорционально её сопротивлению.

---

### User Story 2 - Анализ изменений в сети (Priority: P2)

Инженер изменяет параметры сети (добавляет новые линии, меняет мощности
нагрузок/генераторов, корректирует сопротивления) в JSON-файле и повторно
запускает расчет. Результаты разных запусков позволяют сравнивать влияние
изменений на распределение мощностей.

**Why this priority**: Итеративный анализ — основной рабочий процесс
инженера-проектировщика. Позволяет оценивать решения "что если" без ручного
пересчета.

**Independent Test**: Взять JSON-файл из User Story 1, изменить мощность
нагрузки (например, с 50 МВт на 70 МВт), запустить расчет, убедиться что
напряжения и потоки изменились предсказуемым образом и баланс сохраняется.

**Acceptance Scenarios**:

1. **Given** ранее рассчитанная сеть, **When** инженер увеличивает нагрузку
   на 20%, **Then** токи и потоки мощности перераспределяются, напряжения в
   узлах снижаются пропорционально росту нагрузки, баланс сохраняется.

2. **Given** сеть с существующей топологией, **When** инженер добавляет новую
   ветвь (параллельную существующей), **Then** поток распределяется между
   параллельными линиями обратно пропорционально сопротивлениям.

---

### User Story 3 - Обработка некорректных данных (Priority: P3)

Инженер допускает ошибку при подготовке JSON-файла (опечатка в типе узла,
несуществующий идентификатор ветви, несвязная сеть). Программа выявляет
проблему на этапе валидации и выдает понятное сообщение на русском языке с
указанием конкретной ошибки и рекомендацией по исправлению. Инженер исправляет
файл и успешно повторяет расчет.

**Why this priority**: Качественная диагностика ошибок экономит время инженера
и предотвращает неверные результаты. Без P1 и P2 не имеет смысла.

**Independent Test**: Подготовить JSON-файлы с различными ошибками в разных
островках (отсутствует slack в одном островке, два slack в другом, битая ссылка
в третьем), запустить программу, проверить что для каждого проблемного островка
выведено предупреждение с перечислением всех ошибок, корректные островки
рассчитаны, итоговый код возврата зависит от наличия хотя бы одного успешного
островка.

**Acceptance Scenarios**:

1. **Given** JSON-файл с тремя островками, один из которых без slack-узла,
   **When** инженер запускает расчет, **Then** программа выводит предупреждение
   с указанием номера проблемного островка, пропускает его и рассчитывает
   остальные два островка. Код возврата 0.

2. **Given** JSON-файл, где ветвь ссылается на несуществующий узел, **When**
   инженер запускает расчет, **Then** программа выводит сообщение с указанием
   ID проблемной ветви и несуществующего ID узла.

3. **Given** JSON-файл с несколькими островками, часть из которых имеет ошибки
   валидации, **When** инженер запускает расчет, **Then** программа выводит
   предупреждения для каждого проблемного островка (с перечислением всех ошибок)
   и рассчитывает только корректные островки. Если хотя бы один островок
   рассчитан — код возврата 0; если ни один — код 1.

4. **Given** JSON-файл с нарушением баланса мощностей более чем на 5%, **When**
   инженер запускает расчет, **Then** программа выводит предупреждение с
   фактическим значением невязки и продолжает расчет (предупреждение, не
   ошибка).

5. **Given** входной файл не существует по указанному пути, **When** инженер
   запускает программу, **Then** выводится сообщение: "Ошибка: файл '<путь>'
   не найден. Проверьте путь и повторите запуск."

---

### Edge Cases

- Сеть из двух узлов (slack + нагрузка), одна ветвь — минимальная
  конфигурация. Должна рассчитываться без ошибок.
- Все узлы, кроме slack, являются транзитными (нулевая мощность). Напряжения
  всех узлов должны быть равны напряжению slack (единице в о.е.), потоки по
  ветвям — нулевые.
- Несколько параллельных ветвей между одной парой узлов — эквивалентная
  проводимость должна вычисляться как сумма проводимостей.
- Сеть ровно из 20 узлов (максимальная размерность) — расчет должен
  выполняться без потери точности.
- Что происходит, когда итерационный процесс не сходится за max_iterations?
  Программа выводит предупреждение о несходимости и достигнутой невязке.
- Узел типа "load" с нулевой мощностью (транзитный узел) — допустим,
  обрабатывается корректно (P=0, ток=0).
- Генерация точно равна нагрузке — невязка 0%, расчет выполняется без
  предупреждений.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Программа MUST принимать путь к входному JSON-файлу как аргумент
  командной строки. При отсутствии аргумента MUST использоваться файл по
  умолчанию `data/input.json`.
- **FR-002**: Программа MUST валидировать структуру входного JSON перед
  расчетом: наличие всех обязательных полей, корректность типов,
  уникальность идентификаторов узлов и ветвей.
- **FR-003**: Программа MUST проверять, что все `from_node_id` и `to_node_id`
  в ветвях ссылаются на существующие узлы.
- **FR-004**: Программа MUST выполнять изолированную проверку каждого островка:
  островок без slack-узла или с несколькими slack-узлами → предупреждение и
  пропуск при расчете; островок с другими ошибками валидации → предупреждение
  и пропуск. Расчет выполняется для всех островков без ошибок, в которых есть
  ровно один slack-узел.
- **FR-005**: Программа MUST проверять, что все сопротивления ветвей строго
  положительны (> 0).
- **FR-006**: Программа MUST проверять связность в пределах каждого островка:
  все узлы островка должны быть достижимы от slack-узла этого островка через
  цепочку ветвей. Островки без slack-узла не рассчитываются (предупреждение).
- **FR-007**: Программа MUST проверять баланс мощностей с допустимым
  отклонением 5% (|ΣP_gen − ΣP_load| / max(ΣP_gen, ΣP_load) ≤ 0.05) и
  выдавать предупреждение при превышении.
- **FR-008**: Программа MUST вычислять матрицу узловых проводимостей на основе
  сопротивлений ветвей. Проводимость ветви g = 1/R (См). Диагональные элементы
  Y_ii = сумма проводимостей ветвей со знаком минус, подключенных к узлу i.
  Внедиагональные элементы Y_ij = g_ij для связанных узлов.
- **FR-009**: Программа MUST решать систему линейных уравнений Y×U = I
  относительно напряжений в узлах. Напряжение slack-узла фиксировано.
- **FR-010**: Программа MUST использовать итерационный метод с контролем
  невязки: остановка при max(|U_new − U_old|) < tolerance или по достижении
  max_iterations.
- **FR-011**: При недостижении сходимости за max_iterations программа MUST
  выдавать предупреждение и завершаться с сообщением о несходимости.
- **FR-012**: Программа MUST вычислять потоки активной мощности по каждой
  ветви: P_ij = g_ij × (U_i − U_j) × U_base (в именованных единицах, МВт).
  Знак потока определяется направлением from→to.
- **FR-013**: Программа MUST выводить в консоль три ASCII-таблицы:
  напряжения в узлах (ID, название, U о.е., U кВ), потоки по ветвям
  (ID, название, от, до, P МВт, направление), сводку баланса
  (генерация, нагрузка, невязка, статус сходимости, число итераций).
- **FR-014**: Программа MUST формировать текстовый файл отчета `report.txt`
  с теми же данными в директории запуска.
- **FR-015**: Программа MUST поддерживать сети размером до 20 узлов
  включительно.
- **FR-016**: Программа MUST обрабатывать параллельные ветви (несколько ветвей
  между одной парой узлов) корректно: эквивалентная проводимость = сумма
  проводимостей, распределение потока обратно пропорционально сопротивлениям.
- **FR-017**: Мощность узла типа "load" MUST интерпретироваться как
  потребляемая (P < 0 в уравнениях), мощность типа "generator" — как
  генерируемая (P > 0 в уравнениях), при том что в JSON оба значения задаются
  положительными числами.
- **FR-018**: Все сообщения об ошибках валидации MUST быть на русском языке,
  содержать указание на конкретную проблему и, где возможно, рекомендацию по
  исправлению.

### Key Entities

- **Узел (Node)**: Точка подключения в электрической сети. Характеризуется
  идентификатором, названием, типом (slack/load/generator), заданной мощностью
  (для load и generator) или напряжением (для slack).
- **Ветвь (Branch)**: Линия электропередачи между двумя узлами.
  Характеризуется идентификатором, названием, узлами начала и конца,
  продольным активным сопротивлением.
- **Сеть (Network)**: Совокупность узлов и ветвей с глобальными параметрами
  (базисное напряжение, базисная мощность, параметры сходимости).
- **Результат расчета (CalculationResult)**: Напряжения в узлах (о.е. и кВ),
  потоки мощности по ветвям (МВт, направление), сводка баланса, статус
  сходимости.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Инженер получает результат расчета сети из 20 узлов не более
  чем за 1 секунду после запуска программы (без учета времени на чтение файла
  и вывод).
- **SC-002**: Точность расчета напряжений — не хуже указанного в файле
  значения tolerance (по умолчанию 0.001 о.е.).
- **SC-003**: Баланс мощностей в результатах сходится с точностью не хуже
  1e-6 отн. ед. (сумма потоков, втекающих в узел, равна заданной мощности
  узла).
- **SC-004**: Инженер, допустивший ошибку в JSON-файле, получает сообщение,
  позволяющее локализовать и исправить проблему без обращения к документации
  (сообщение содержит ID сущности, тип ошибки и рекомендацию).
- **SC-005**: Результаты расчета для простой сети (2-3 узла) совпадают с
  ручным аналитическим расчетом с точностью до 4 значащих цифр.
- **SC-006**: Программа корректно обрабатывает все перечисленные в спецификации
  ошибочные ситуации (10 категорий ошибок) с выводом понятного сообщения и
  ненулевым кодом возврата.

## Assumptions

- Входной JSON-файл использует кодировку UTF-8.
- Базисное напряжение и базисная мощность заданы в JSON-файле явно и являются
  положительными числами.
- Потери в линиях не учитываются (модель DC power flow без потерь), поэтому
  сумма генерации равна сумме нагрузки в результатах расчета (в пределах
  точности метода).
- Итерационный метод сходится для корректно заданных сетей постоянного тока
  при стандартных параметрах (tolerance=0.001, max_iterations=100).
- Параллельные ветви с одинаковыми from_node_id и to_node_id считаются
  независимыми линиями с собственными сопротивлениями.
- Программа является консольным приложением, не требующим графического
  интерфейса.
- Операционная система: Linux (основная цель), совместимость с Windows и macOS
  желательна, но не обязательна для v1.
